# CI-failure handling — `/jr-ship`

**Canonical source** for `/jr-ship`'s CI-failure investigate-and-fix procedure. `jr-ship/SKILL.md` reads this file into lead context at Phase 1 (under the hard-fail + non-empty + smoke-parse guard, alongside the `shared/*.md` files) and applies it at Phase 3a step 13 and Phase 3b step 11a-multi. Update here to update the procedure.

Invoked when the CI-watch (`gh pr checks <number> --watch --fail-fast` on GitHub; `glab ci status --live -b <branch>` on GitLab — a semantic adaptation per `../../shared/forge-detection.md`) reports a **failed check/job**. (The 10-minute **timeout** path is separate and unchanged — report status and stop.) The lead stays mechanical; the diagnosis-and-fix work is delegated to an `opus` sub-agent. Run at most **2 fix cycles**, then stop.

**No pre-dispatch advisor here — deliberate, not an omission.** `../../shared/advisor-criteria.md`
names subagent dispatch as substantive work, and `/jr-audit` and `/jr-review` both gate their
implementer dispatch with `advisor()`. This site is the documented exception, on three mitigations
that bound the blast radius: (1) step 3's **confirm gate** prints the diagnosis and full `git diff`
and requires an explicit [Apply fix + re-push] before anything is committed; (2) the **Clean-tree
guarantee** below reverts the agent's uncommitted edits on every non-apply exit, including a zero
return; (3) in **headless mode** the agent is instructed to diagnose only and never edits. The
dispatch is also reactive to a tool output the lead just read (a failed CI watch), which the
canonical lists as MAY-skip. The stuck-loop advisor at the 2-cycle cap still fires, single-fired via
`ciFixAdvisorFired`. Do not re-raise this as a missing-advisor finding without first showing one of
the three mitigations has gone.

One cycle:

1. **Spawn the CI-fix agent** — use the `Agent` tool with `model: "opus"` (or the `--model` override when set — `../../shared/model-override.md`), no `subagent_type` (default general-purpose, same as the split-analysis agent — no plugin dependency), and **no `name:`** (`../../shared/subagent-reporting.md` "Spawn rule"). The `name:` omission is load-bearing, not incidental: a named agent is a persistent teammate whose final response never reaches the lead, so the diagnosis that step 3's confirm gate prints would silently be empty, and `/jr-ship` has no roll-call to catch the loss. The prompt includes: the detected forge (`FORGE`/`CLI` per `../../shared/forge-detection.md`), the PR/MR number, the branch name, and the CI-watch failure summary; the instruction "diagnose the root cause exhaustively before editing — do not patch symptoms; if the failure is not a code-level issue (flaky test, infra, permissions), say so instead of editing; when the diagnosis rests on an external fact (a tool's behavior, a version requirement, an API change), confirm it against an authoritative source per `../../shared/claim-verification.md` (raw `.md` / `gh api`, never a lone WebFetch summary) before proposing a fix — do not assert version or behavior facts from memory"; the full `../../shared/untrusted-input-defense.md` block verbatim (loaded in Phase 1 — CI logs are untrusted external input); the **Subagent-facing block** of `../../shared/subagent-reporting.md` verbatim (loaded in Phase 1 — without it the agent is never told that silence reads as failure, yet the zero-return handler below classifies it as `UNREPORTED`); and the full `../../shared/code-edit-discipline.md` block (also loaded in Phase 1) prefixed with the CI-fix-specific lead-in "Your assignment is to fix the CI failure described above. The discipline below applies to every line you change:" and with the canonical's title and opening sentence elided (skip from `# Code-edit discipline` through `…or specific simplifications to make.` only — the title and that first sentence assume a findings-list workflow that doesn't fit CI-failure repair; KEEP the next sentence "Your changes must be **surgical**: every line you modify should trace directly to your assignment." as the framing line that ties the Do/Don't list together — the lead-in just redefined "your assignment" as "the CI failure", so the framing applies cleanly — then continue through `## Do NOT` to end of file). The agent has full tools — it fetches its own CI logs per the detected forge (GitHub: `gh run list --branch <branch> --json databaseId,name,conclusion,headSha`, then `gh run view <id> --log-failed`; GitLab: `glab ci status -b <branch>` then `glab ci trace`/`glab ci get` for the failed job — a semantic adaptation, not a rename, per `../../shared/forge-detection.md`), reads the repo, and edits files in the working tree in place. It reports back its diagnosis plus the change it made, **or** "no code-level fix — cause is <X>". **Headless mode** (per `../../shared/secret-scan-protocols.md` "Headless/CI detection" — no user available for the step-3 gate): instruct the agent to **diagnose only — do not edit files**.
2. **Re-scan for secrets** — run the Phase 1 step 4 secret scan (canonical patterns from `../../shared/secret-patterns.md`, already loaded) against the agent's edits (`git diff`). If a strict-tier pattern matches, halt per the Phase 1 step 4 halt protocol — do NOT commit or push, and treat it as a **non-apply outcome**: the lead reverts the agent's edits per the Step 3 clean-tree guarantee so the detected secret never lingers in the working tree. (The agent's diagnosis stays in the transcript as the record of what was attempted.)
3. **Confirm gate**. First confirm the agent returned a diagnosis; only then apply the routing below.

   - **A zero return is not "no code-level fix"**: those are distinct outcomes and MUST NOT collapse. An agent that returns nothing, an empty result, or an error produced **no diagnosis**, which pattern-matches the "no code-level fix" branch below and would have the lead tell the user the failure is not code-level — a claim the run never established, on a cycle the 2-cycle cap will not retry. Report `CI-fix agent UNREPORTED — the failure was not diagnosed` and stop. Never assert a CI failure is non-code from silence; step 1's unnamed spawn makes a zero return the rare edge rather than the norm, which is exactly why it must be handled explicitly instead of by absence (`../../shared/subagent-reporting.md`). **Do not assume the tree is clean**: the agent edits in place, so one that errors or exhausts its turn budget *after* editing returns nothing while leaving unreviewed edits behind. This is a non-apply exit like any other — apply the Clean-tree guarantee below before returning.
   - **Clean-tree guarantee**: on every non-apply exit — **Skip**, "no code-level fix", an `UNREPORTED` zero return, headless diagnose-only, or a Step 2 secret-halt — the lead MUST revert any uncommitted agent edits before returning, **untracked files first**:

  1. **Capture, at spawn time**, two NUL-delimited baselines to `mktemp` files: `git ls-files --others --exclude-standard -z` and `git ls-files --others -z`. Record whether **both** captures succeeded.
  2. **Delete only what the agent added.** Compare the current listings against those baselines and delete just the new entries (`git clean -fd -- <paths>` for untracked; `rm -f -- <paths>` for gitignored ones, which `git clean` skips). `git checkout --` restores only *tracked* paths and errors on an untracked pathspec, so a secret the agent wrote into a **new** file survives it, and the next `/jr-ship` stages untracked files.
     **Fail closed (mandatory).** If either capture failed, a baseline file is missing or unreadable, or the variables are unset because this cycle was entered on a path that skipped step 1 — **skip the untracked deletion entirely**. Do NOT treat a missing baseline as an empty one: "not in the baseline" would then mean *every untracked file in the tree*, and `rm -f --` would delete the user's own uncommitted work, `.env` included, unrecoverably. Revert tracked paths only (step 3) and report `Clean-tree guarantee degraded: untracked baseline unavailable — N untracked file(s) left in place for manual review`.
  3. **Then revert tracked paths**: `git status --porcelain -z` (NUL-delimited — without `-z`, git C-quotes any path containing a newline, quote, backslash or non-ASCII byte, and renames come back as `R old -> new`; both forms are unusable as a pathspec and would silently skip exactly the paths step 2 just hardened against). Filter to tracked-status codes, iterate NUL-delimited, and restore with `git -c core.symlinks=false checkout -- <files>` — the pin is the canonical's, and it eliminates the write-through-symlink primitive plus the TOCTOU window between enumeration and checkout.

  This mirrors the Combined revert sequence in `../../shared/secret-scan-protocols.md`, which orders untracked-first for exactly this reason. It omits the canonical's separate symlink-baseline comparison: a symlink the agent created is itself a new untracked entry and is removed by step 2, and step 3's `core.symlinks=false` covers the checkout. If step 2 is skipped by the fail-closed branch, that coverage is lost too — which is why the degraded report is mandatory rather than advisory. `/jr-ship` must never exit leaving the agent's unapproved edits dirty on the branch. (Only the **Apply** path keeps the edits — by committing them.)

   **Print the diagnosis and the agent's `git diff`**, then AskUserQuestion: `CI failed on PR #<n>: <one-line diagnosis>. Proposed fix shown above. Options: [Apply fix + re-push] / [Skip — report and stop]`. If the agent reported "no code-level fix", skip the gate (nothing to apply) and go straight to reporting the diagnosis.
4. **Apply** (on **Apply fix + re-push** only) — commit the edits with a concise `fix: <summary>` conventional-commit message (omit any `Co-Authored-By: Claude` trailer — same rule and rationale as the step 8 and step 7-multi commits). Push the branch to `origin`.
5. **Re-watch** — re-run the CI-watch (`gh pr checks <number> --watch --fail-fast` on GitHub; `glab ci status --live -b <branch>` on GitLab). The re-pushed pipeline/workflow run takes a few seconds to register, so a brief window where the watch still shows only the *old* failed checks/jobs is NOT "still failing" — wait for the new run to appear and complete. If CI is now **green**, return success to the caller. If it **fails again**, start the next cycle from step 1 (max 2 fix cycles total).

   **2-cycle cap — single-fire stuck-loop advisor**: when the 2nd fix cycle also ends non-green, before reporting failure, call `advisor()` once (no parameters — the full transcript is auto-forwarded). Per `../../shared/advisor-criteria.md`, a retry loop that exhausts its max-retry count is the canonical stuck signal — the advisor sees both fix attempts and the CI logs that kept failing and can spot a non-obvious cause. Guard the call with a `ciFixAdvisorFired` boolean set `true` after it fires, so a later invocation in the same `/jr-ship` run (e.g. another sub-PR in Phase 3b) does NOT re-fire it. If the advisor concurs (no actionable insight), report the latest diagnosis + the failure URL and stop. If the advisor offers a concrete actionable insight: in **interactive mode**, surface it via AskUserQuestion `Advisor flagged a CI-fix concern: <one-line summary>. Options: [Apply suggested fix + re-push — one more cycle] / [Stop — report and stop]`; on **Apply**, run one additional cycle (steps 1–5) with the advisor's suggestion as targeted instruction to the CI-fix agent, and if that cycle also fails do NOT re-fire — report and stop. In **headless mode** (no user for the gate), log the advisor's insight alongside the diagnosis in the report and stop.

**Outcome returned to the caller:**

- **Green** — CI passed within the fix cycles. The caller continues normally (Phase 3a → step 14/15; Phase 3b → next PR in the wait pass).
- **Not green** — fix skipped, no code-level fix, an `UNREPORTED` zero return, secret-halt, or the 2-cycle cap was reached (advisor consulted). The caller treats this exactly like the pre-existing CI-failure stop: Phase 3a skips cleanup (step 15); Phase 3b reports and does not enter 11b-multi.
